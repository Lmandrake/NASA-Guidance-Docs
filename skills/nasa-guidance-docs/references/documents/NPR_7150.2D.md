## What it is for, plainly

This is NASA's Agency-wide rulebook for how software gets engineered: planning, developing, testing, maintaining, retiring, operating, managing, acquiring, and assuring it (P.2 item b, p.4). It does not apply the same way to every piece of software — each requirement is switched on or off by a software "class" (Appendix D) and recorded in a project's own Requirements Mapping Matrix (Appendix C). For JPL, an FFRDC, the NPR itself does not bind directly; it reaches JPL only when a contract, grant, or agreement says so (P.2 item a and its Note, p.4).

## What it obliges (or advises)

- Appendix A defines "Safety Critical" for the whole document, sourced from another NPR rather than coined here:

> "Safety Critical. A term describing any condition, event, operation, process, equipment, or system that could cause or lead to severe injury, major damage, or mission failure if performed or built improperly, or allowed to remain uncorrected. (Source NPR 8715.3)"

— NPR 7150.2D, Appendix A, p.49. ⚠️ **Page correction:** this definition sits entirely on p.49, immediately before the page break to p.50 — not pp.49–50 as sometimes cited. The definition is written for "any... system," not only software, so it reaches a system with a learned component inside it with no edit (our reading).

- Classify every system and subsystem containing software into Class A–F per Appendix D (3.5 / SWE-020, p.24).
- Determine, with the SMA organization, whether each software component is safety-critical, "per the criteria defined in NASA-STD-8739.8" (3.7 / SWE-205, p.26).
- If safety-critical, implement NASA-STD-8739.8's safety-critical software requirements (SWE-023, p.26) and twelve named software behaviors — known-safe initialization, safe state transitions, operator-override independence, rejecting out-of-sequence commands, memory-modification detection, I/O integrity checks, prerequisite checks, no single event triggering a hazard, timely response to off-nominal conditions, error handling, and the ability to reach a safe state (SWE-134, p.26).
- If safety-critical, reach 100 percent code test coverage under the Modified Condition/Decision Coverage (MC/DC) criterion (SWE-219, pp.26–27) and keep cyclomatic complexity at 15 or lower, with any exceedance reviewed and waived with rationale (SWE-220, p.27).
- Define the approach to automatic generation of software source code, covering seven named items (3.8.1 / SWE-146, p.27). Verbatim:

> "3.8.1 The project manager shall define the approach to the automatic generation of software source code including: [SWE-146]
> a. Validation and verification of auto-generation tools.
> b. Configuration management of the auto-generation tools and associated data.
> c. Description of the limits and the allowable scope for the use of the auto-generated software.
> d. Verification and validation of auto-generated source code using the same software standards and processes as hand-generated code.
> e. Monitoring the actual use of auto-generated source code compared to the planned use.
> f. Policies and procedures for making manual changes to auto-generated source code.
> g. Configuration management of the input to the auto-generation tool, the output of the auto-generation tool, and modifications made to the output of the auto-generation tools."

— NPR 7150.2D, §3.8.1, p.27

⚠️ **Common paraphrase trap (our reading).** This is often summarized as "auto-generated code must be verified to the same standard as hand-written code." The binding verb is "define the approach" — a planning obligation on the project manager, not a performance obligation to actually run equal verification. The "same standards and processes" wording in item d attaches to the generated **source code**, not to the generation tool; item a asks only for the tool's own "validation and verification," with no equal-standard clause.

- Require NASA electronic access to the models, simulations, and associated data used as inputs to auto-generation (3.8.2 / SWE-206, pp.27–28).
- For COTS/GOTS/MOTS/OSS/reused components: identify requirements the component must meet, verify and validate it "to the same level required to accept a similar developed software component" (SWE-027, p.22), and test embedded reused components "to the same level required to accept a custom developed software component" (SWE-211, p.37).
- For projects reaching Key Decision Point A, ensure software independent verification and validation (IV&V) on: NPR 7120.5 Category 1 projects; NPR 7120.5 Category 2 projects with Class A or Class B payload risk classification per NPR 8705.4; and projects the Mission Directorate Associate Administrator explicitly selects (SWE-141, pp.25–26).

## Where it stops

- **Class-gated.** A requirement binds a given system only where Appendix C marks that requirement applicable to that system's software class (SWE-139, p.22).
- **Class E cannot be safety-critical software**, by definition: "Class E software cannot be safety-critical software. If the software is classified as safety-critical software, then it has to be classified as Class D or higher" (Appendix D, p.69).
- **Names the artifact, never the method.** The words "artificial intelligence," "machine learning," "neural," "autonomy," and "autonomous" do not occur in a text search of the public PDF. The document regulates "auto-generated code" (Appendix A, p.50) as a category of software product, without naming how that code came to be generated.
- **Tailoring is bounded, not free.** Relief from an "X" requirement is granted only by designated Technical Authorities (Engineering and SMA, or the NASA CIO for security issues), recorded in a project's Requirements Mapping Matrix, with risk and rationale documented for anything relieved (p.22). Chapter 2's own requirements sit outside the Requirements Mapping Matrix entirely (p.10).

## AI and machine-learning touchpoints

- The NPR itself contains no AI- or machine-learning-specific text; every point below is the companion Software Engineering Handbook's reading of this NPR's requirements, not new text in the NPR (our reading).
- NASA-HDBK-2203 topic 7.25 §7 states: "All NPR 7150.2 SWEs are applicable to AI/ML software," and walks through several — e.g., reading SWE-146 (auto-generated code) as covering a trained model's output, and SWE-206 (auto-generation inputs) as reaching the model and its training/associated data (topic 7.25 §7.2; see `NASA-HDBK-2203.md` in this reference set).
- SWE-205's determination of safety-criticality (NASA-STD-8739.8's criteria) is the gate the Handbook points to before any AI-enabled component could be used in a safety-critical role at all (topic 7.25 §5, citing SWE-205).
- SWE-219's 100 percent MC/DC coverage and SWE-220's cyclomatic-complexity ceiling are both measures over source-code branches; neither measures what a learned component's weights or training data do, which is a limit of the metric rather than a statement in this NPR (our reading).

## How it connects to other documents

- Invokes NASA-STD-8739.8 for safety-critical criteria and requirements (SWE-205, SWE-023, p.26) and for software assurance and IV&V planning generally (SWE-022, p.25).
- Invokes NPR 8705.4 for payload risk classification, used inside the SWE-141 IV&V gate (p.25).
- Points readers to NASA-HDBK-2203 for guidance on several requirements, including SWE-220 ("For more guidance on this requirement, see NASA-HDBK-2203," p.27).
- NASA-STD-8739.8B lists NASA-HDBK-2203 among its own Applicable Documents and, by our check, disagrees with this NPR's own Appendix C on the section references for two shared requirements (SWE-032 and SWE-086) — a recorded NASA-vs-NASA inconsistency, not a defect in either document considered alone.
- Chapter 2 sets the roles that administer this NPR: the Office of the Chief Engineer (OCE) leads the software engineering initiative, benchmarks Centers, authorizes appraisals, and reviews Requirements Mapping Matrices (SWE-002, SWE-004, SWE-129, SWE-152, pp.10–11); the NASA Chief, Safety and Mission Assurance (SMA) is Technical Authority for the NPR's requirements, leads software assurance/safety initiatives, and makes the final call on tailoring SWE-141 (SWE-208, SWE-223, pp.11–12); Center Directors, or designee, establish and maintain Center software processes, comply with Appendix C's "X" marks, and maintain Center software inventories (SWE-005, SWE-140, SWE-006, pp.12–14). Tailoring approval runs through these Technical Authorities via the Requirements Mapping Matrix (Appendix C), not through this NPR's text directly.

## Traps

- Pulling the SWE-146 obligation apart from its stem: the "shall" lives in the opening sentence ("the project manager shall define the approach…"); items a–g are themselves modal-free and inherit their force entirely from that stem.
- Treating "Class E cannot be safety-critical" as a general safety ceiling: it is a classification-eligibility rule, not a statement that Class E software is risk-free — a defect found safety-critical simply forces reclassification to Class D or higher (p.69).
- Assuming the NPR's silence on AI/ML means NASA has no guidance here: the silence is in this document only. NASA-HDBK-2203 topic 7.25/8.25 fills that gap as guidance, not as a requirement (see `NASA-HDBK-2203.md`).
- Reading this NPR as binding JPL directly: P.2 item a's own Note says the applicability statement "alone is not sufficient to stipulate requirements for the contractor" — it becomes mandatory at JPL only through contract clauses, specifications, or statements of work that invoke it.
