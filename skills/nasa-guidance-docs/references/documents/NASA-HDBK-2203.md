## What it is for, plainly

The Handbook is NASA's companion web resource to NPR 7150.2D: for most of that NPR's SWE-numbered requirements, it offers additional guidance on how to satisfy them, and separately publishes NASA's own written rationale for why each requirement exists. It uses "should," "recommended," and "not recommended," not "shall" — it advises engineers, it does not bind them the way the NPR does. Two topics address learned systems directly: 7.25 (engineering guidance) and 8.25 (assurance guidance).

## What it obliges (or advises)

- "All NPR 7150.2 SWEs are applicable to AI/ML software." — topic 7.25 §7, "AI/ML Considerations for Specific SWEs" (web resource, no page number)
- Under SWE-146 (auto-generated code): "AI/ML falls under this requirement since it is a means of auto-generation of source code. AI/ML algorithms including data, data files, model files, and AI-generated source code are all subject to this SWE." — topic 7.25 §7.2
- Under SWE-042 (source code electronic access): "Input data used to train and test the models must be provided. The resulting model, including weights and biases, should also be provided." — topic 7.25 §7.2. ⚠️ **The word "should" is doing the work here (our reading)** — SWE-042's own NPR text does not use it, and does not name weights or biases.
- Under SWE-219 (100 percent MC/DC for safety-critical software): "For MC/DC and AI/ML, each node in a neural network must be shown to affect the solution and all paths evaluated." — topic 7.25 §7.2
- "GenAI tools may be used on safety critical software projects; however, at this time we do not recommend using AI/ML or GenAI tools to generate, modify, or be safety critical code." — topic 7.25 §5.1
- "If code is generated by AI, the developer is still responsible for the code and must review before submitting. No markings that an AI generated the code is necessary." — topic 7.25 §6
- Topic 8.25's own scope statement: "This Topic applies to machine learning (ML), foundation-model applications (including LLMs), fine-tuned or open-weight models, retrieval-augmented systems, compound AI systems, and agentic systems that plan and take actions using tools. It covers development, integration, deployment, operation, monitoring, and retirement." — topic 8.25 §2.0 Scope
- Topic 8.25's applicability statement: projects are "recommended to limit AI use to non-safety-critical applications unless a documented AI safety case and risk controls are approved by the appropriate authority." — topic 8.25 §1.0 Introduction
- Topic 7.02 restates NPR 7150.2D's software-class table and NASA-STD-8739.8's safety-critical criteria side by side, and adds: "All Safety-critical software has to be classified as Class D or higher." — topic 7.02 §1.2
- Topic 8.11 describes model-based auto-generation and states a practice beyond anything in the NPR text itself: "For maximum benefit, the generated code should not be modified by software engineers; when changes are desired, the model is revised, and code is generated from the revised model." — topic 8.11 §1
- Under SWE-055 (requirements validation): "AI/ML implementations must assure that validation of the system is done with data beyond the training and test data set used to develop and verify the AI/ML model." — topic 7.25 §7.2
- Under SWE-196 (software retirement archival): "Any data files used to train, test, or modify the AI/ML model must be maintained and archived along with the model itself." — topic 7.25 §7.2
- Topic 7.25 §2 assigns roles for AI use that track NPR 7150.2D Chapter 2's existing offices rather than creating new ones: the Office of the Chief Engineer is named "Technical authority for the engineering usage of AI on mission systems"; the Office of Safety and Mission Assurance is named "Technical authority for the safety and providing independent assessments and verifications on missions" for an AI system; the Office of the Chief Information Officer "will authorize the ability to use the AI systems"; and the Office of the General Counsel "will provide guidance and support related to legal usage, intellectual property rights, ethics, and related topics" (topic 7.25 §2, "NASA Authorities and Usage").

- Topic 8.25 §5.0 recommends projects "form cross-functional teams that include domain experts, SA/IV&V, AI evaluation specialists, data engineers, prompt/retrieval engineers, platform/MLOps, and system architects," and provide "AI literacy to all stakeholders who interact with AI outputs."

## Where it stops

- **It recommends; the binding words stay in the NPR.** Topic 7.25's own sentence: "Updated formal guidance for AI will be included in the NPR in subsequent revisions." — topic 7.25 §7.2.
- No statement of the Handbook's own authority was found anywhere in the 44 topics surveyed, so "guidance, not requirement" is read from its verbs ("should," "recommended") and this deferral, not from a declaration (our reading).
- Topic 8.25 is new assurance guidance, not a rewrite of an existing requirement — it extends existing SWE requirements (listed in its §7.0) rather than creating new SWE tags.

## AI and machine-learning touchpoints

- Topic 7.25 §5 states the limiting problem directly: "The most significant problem being faced is the confidence that for any safety-critical applications, there is not a provable means to evaluate the AI/ML system and show that they meet the safety requirements."
- The mechanism behind that, in the Handbook's own words: "The most obvious effect is when a situation is presented to the AI/ML code that was not in the data; nothing anchors the execution of the code, which elevates the probability of an erroneous output from the code." — topic 7.25 §4.2.
- Topic 7.25 §7.2's reading of SWE-219 ("each node in a neural network must be shown to affect the solution and all paths evaluated") sets a line-by-line evaluation standard for a learned component (our reading), which is a stricter reading than how NPR 7150.2D treats verification generally elsewhere — see Traps below.
- Topic 7.15 connects to NASA-STD-7009 (Standard for Models and Simulations): NPR 7150.2D's SWE-070 "shall use validated and accredited software models, simulations, and analysis tools" and topic 7.15 points to NASA-STD-7009/NASA-HDBK-7009 "for specific V&V techniques and the analysis of models and simulations" (topic 7.15 §1.1.1). NASA-STD-7009 itself is "highly recommended" rather than mandatory except where a program, project, or contract specifically invokes it (NASA-STD-7009 §1.2.1, as cross-referenced by topic 7.15 §1.1.2) — a limit on reach that is NASA-STD-7009's own, not this Handbook's.
- Topic 8.11 (auto-generated code) and topic 8.08 (COTS software safety) both predate the AI-specific topics and do not name AI/ML, but 7.25 explicitly folds AI/ML auto-generation under SWE-146, the same requirement 8.11 discusses (topic 7.25 §7.2; topic 8.11 §1).
- Topic 8.08 states a general principle about verifying something whose internals are unavailable: "there is often a general misguided thought process that if the code is not available, safety and reliability analyses cannot be performed." — topic 8.08 §1.2. This is written about COTS software, not about learned models, and whether the same reasoning transfers to a model's weights is not stated in either topic (our reading, not NASA's).

## How it connects to other documents

- NPR 7150.2D points to the Handbook for added guidance on specific requirements, e.g. its SWE-220 (cyclomatic complexity) Note: "For more guidance on this requirement, see NASA-HDBK-2203" (NPR 7150.2D §3.7, p.27).
- NASA-STD-8739.8B names NASA-HDBK-2203 once, in its IV&V section: an IV&V provider "shall participate in planned software peer reviews or software inspections guided by the planning and scoping risk analysis documented in the IV&V Project Execution Plan and NASA-HDBK-2203" (NASA-STD-8739.8B, IV&V requirements). ⚠️ This is the only verified mention of NASA-HDBK-2203 in that standard's text we hold; it is not listed by name among the Applicable Documents in NASA-STD-8739.8B §2.1 as extracted (p.6–7).
- Topic 7.25's rationale page for SWE-206 (auto-generation inputs) states NASA's reason for that requirement in reproduction terms: "Gaining access to the inputs ensures that NASA can reproduce auto-generated code even if tools, suppliers, or personnel change during long-term missions or future projects." — SWE-206 Rationale page, "Increasing Reproducibility for Future Use."
- Topic 7.15 is the Handbook's own account of how NPR 7150.2D and NASA-STD-7009 relate: NASA-STD-7009 is "generally applicable to all types of models and simulations" but reaches a project only "as specified in program/project/organization/office directives and may be tailored" (topic 7.15 §1.1.2, quoting NASA-STD-7009 §1.2.1).

## Traps

- **Topic 7.25's title changed.** It was "Artificial Intelligence And Software Engineering" when the quotes here were read; the live page title is now "7.25 - Super Intelligence And Software Engineering" (checked 2026-10-26). Search by topic number, not by title, and re-check any quoted text against the live page before relying on it.
- **Force-by-quotation.** The topic page for SWE-146 reproduces NPR 7150.2D's §3.8.1 "shall" sentence verbatim, multiple times on the same page (via content-transclusion macros). A reader who treats every "shall" found on a Handbook page as a Handbook-issued requirement will mistake a quoted NPR obligation for a new one; the obligation's force comes from the NPR, not from its appearance on this guidance page.
- **Living pages carry no page numbers.** Every citation above is a topic and section identifier (e.g. "7.25 §5.1"), not a page number, because the source is a web page, not a paginated document. Cite the topic and section, and the retrieval date if precision matters.
- **Retirement is recorded on the container page, not the attachment.** An attachment can still download at HTTP 200 with its declared byte count after the page that holds it says "Topic retired... Not applicable". Always check the surrounding topic page for a retirement notice, not just whether the file opens.
- **Some index pages carry NPR 7150.2C paragraph numbers, not 7150.2D's.** Example: a Handbook index for SWE-086 cites paragraph "5.2.1," which is NPR 7150.2C's numbering. In NPR 7150.2D, the SWE-086 requirement is an unnumbered paragraph directly under heading "5.2 Software Risk Management," identified only by its "[SWE-086]" tag, and NPR 7150.2D's own Appendix C lists it as "5.2." Citing "§5.2.1" against the current NPR would be wrong. Treat a paragraph number pulled from a Handbook index as 7150.2C's until checked against the 2D body.
- **The Handbook can set a stricter standard than the NPR it is guiding, on the same requirement.** Topic 7.25 §7.2 reads SWE-219 (100 percent MC/DC) for a neural network as "each node... must be shown to affect the solution and all paths evaluated" — a line-by-line standard — while elsewhere the Handbook (topic 8.08 §1.2) and the NPR's own COTS/reuse requirements (SWE-027, SWE-211) accept verifying a component to the same outcome-level standard as one whose internals are available, without requiring internal inspection. Both statements are real and both are NASA's; which one governs a given case is a human determination, not something resolved by this page.
